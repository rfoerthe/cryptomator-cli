# Design spec: `crypto` – Rust CLI port of Cryptomator

_As of 2026-09-04. Derived from the approved planning document; serves as the reference for all implementation plans._


## Context

Cryptomator (JavaFX, GPLv3) has no full-featured CLI; the official `cryptomator/cli` (Java) can only do `unlock` + `list-mounters` and needs a JVM. The goal is a new, standalone Rust tool **`crypto`** in the directory **`/Users/rfoerthe/work/cryptomator-cli`** (currently empty, will become its own git repository) that offers every function of the desktop app as a CLI, is built for macOS and Linux, and stays compatible with the vaults, the `settings.json` and the keychain entries of the desktop app.

The vault format does **not** live in the Cryptomator repository, but in `cryptolib 2.2.2` and `cryptofs 2.10.0`. The sources JARs are available locally and are the porting template (read them without unpacking: `unzip -l <jar>` / `unzip -p <jar> <path>`):

- `~/.m2/repository/org/cryptomator/cryptolib/2.2.2/cryptolib-2.2.2-sources.jar`
- `~/.m2/repository/org/cryptomator/cryptofs/2.10.0/cryptofs-2.10.0-sources.jar`
- `~/.m2/repository/org/cryptomator/siv-mode/1.6.1/siv-mode-1.6.1-sources.jar`
- `~/.m2/repository/org/cryptomator/fuse-nio-adapter/6.0.1/fuse-nio-adapter-6.0.1-sources.jar` (mount provider: capabilities, default flags, detection, unmount)
- `~/.m2/repository/org/cryptomator/integrations-mac/1.5.0/integrations-mac-1.5.0-sources.jar` (keychain)
- Desktop app: `/Users/rfoerthe/work/pro/cryptomator/.claude/worktrees/cryptomator-cli-rust-be5387/src/main/java/org/cryptomator/…`

## Decisions taken (settled with the user, design approved)

| Topic | Decision |
|---|---|
| Approach | Own port using RustCrypto crates, no dependency on oxcrypt/cryptomator-rs |
| License | AGPL-3.0 (cryptolib/cryptofs are AGPLv3) |
| Mount | FUSE via `fuser` (Linux libfuse3; macOS macFUSE **or** FUSE-T, chosen at run time) + WebDAV loopback fallback (port 42427, `--port 0` for a free one) + mountless `fs` commands |
| Configuration | Share the desktop `settings.json`, schema-compatible |
| Process model | Background daemon per vault with a Unix socket; `--foreground` optional |
| Hub vaults | Detect (`kid` starts with `hub+`) and reject with a clear error message (exit 9) |
| Out of scope | Theme, windows, language, tray, compact mode, update check, supporter certificate, autostart/auto-unlock at login (those fields are merely preserved in settings.json) |

## Key technical findings (verified against the sources)

1. **FUSE-T cannot be driven directly with `fuser`.** FUSE-T has no `/dev/fuse`; `libfuse-t.dylib` is a libfuse-2.9 API-compatible library with an NFS/SMB userspace server. `fuser` speaks the kernel FUSE protocol over an fd. The only way for a single binary that picks at run time: `dlopen` the vendor dylib (`/usr/local/lib/libfuse.2.dylib` macFUSE, `/usr/local/lib/libfuse-t.dylib` FUSE-T; those exact paths are what `MacFuseMountProvider`/`FuseTMountProvider` check), call `fuse_mount_compat25(mountpoint, &fuse_args) -> fd` (the symbol used by fuser's own `src/mnt/fuse2.rs`) and hand the fd to `fuser::Session::from_fd`. Safe for macFUSE, for FUSE-T a **spike (M0) with go/no-go**; fallback: a `fuse_lowlevel_ops` FFI backend for FUSE-T only (like jfuse).
   **Spike A result (M0, [`docs/superpowers/spikes/2026-09-04-spike-a-fuse-t.md`](../spikes/2026-09-04-spike-a-fuse-t.md)): FUSE-T 1.2.7 with an unmodified fuser 0.18 is a NO-GO.**
   Transport and handshake work (`dlopen` → `fuse_mount_compat25` → `fuser::Session::from_fd`, `proto=7.19` negotiated, real kernel FUSE requests flow); the obstacle is purely the struct ABI:
   under `target_os = "macos"` fuser writes the macFUSE `fuse_attr` layout (104 B, with `crtime`/`crtimensec`, `flags` before `blksize`), while FUSE-T parses the Linux layout (88 B) — so `mode` arrives as 0 and FUSE-T aborts the mount.
   **Decision for M4:** stay with `fuser`, but with a Linux ABI feature (fork/patch of `fuse_abi.rs` that makes the `#[cfg(target_os = "macos")]` fields switchable; suitable for upstream as a feature flag), verified by a follow-up spike before the implementation. macFUSE is **untested** (not installed) and is not affected by the root cause.
2. **The `keyring` crate is unsuitable** (it looks for `service`/`username`). Desktop schema: macOS generic password in the login keychain, service `"Cryptomator"`, account = vault ID, password UTF-8 → use `security-framework` directly. Linux Secret Service: login collection, label `"Cryptomator"`, attributes `{"Vault": id, "Name": displayName}`, search only via `{"Vault": id}` → use the `secret-service` crate directly. KWallet (folder `Cryptomator`, key = ID) optional/later.
3. **settings.json asymmetry**: the desktop app ignores unknown keys when reading and **discards them on the next save**. The CLI must preserve unknown keys (serde `flatten`), but must **not put any CLI-owned state into settings.json** → a separate `cli.json` next to settings.json. Checked locally: `~/Library/Application Support/Cryptomator/settings.json` (written by 1.19.3) matches `SettingsJson` exactly.
4. **AES-SIV key order**: cryptolib calls `siv.encrypt(encKey /*CTR*/, macKey /*S2V*/)`. RFC 5297/RustCrypto `Aes256Siv`: first half = S2V key, second = CTR key → **Rust key = macKey ‖ encKey**.
5. **Java streaming-writer quirk**: `EncryptingWritableByteChannel.close()` always writes a final chunk, even an empty one. The root directory's `dirid.c9r` (dirId `""`) = header + empty chunk (SIV_GCM: 68 + 28 = 96 bytes); `cleartextSize()` throws for that size. Our stream writer has to mirror this; the chunk-cache path never writes empty chunks.
6. **Mount provider facts** (fuse-nio-adapter 6.0.1) have to be reproduced exactly so that `mountFlags` in settings.json stays valid (see `cryptomator-mount`).
7. **mountPointsDir**: Linux `~/.local/share/Cryptomator/mnt`; the macOS build script is missing a slash (upstream typo). We use `~/Library/Application Support/Cryptomator/mnt` and document the deviation.
8. **Legacy cryptofs on Maven Central**: 1.9.15 (format 7), 1.8.9 (format 6) and — instead of the planned 1.6.2, which already writes format 6 — 1.3.2 (format 5) are available, but are **not** in `~/.m2`: the first generator run needs the network. The *committed* fixtures need none; only regenerating downloads these three artifacts, and the interop run against cryptofs 2.10.0 gets by without them.
9. **Local environment**: macOS 26.6.2, cargo 1.98, pkg-config, Java 26 + jshell + Maven. **No FUSE installed** (neither macFUSE nor FUSE-T). For spike A and the FUSE tests the user has to install FUSE-T (`brew install --cask macos-fuse-t/homebrew-cask/fuse-t`) or macFUSE; until then build/test the WebDAV feature. Because the dylib is loaded via `dlopen`, the build itself needs no FUSE.
10. **Spike B (reading a desktop keychain entry) is BLOCKED, not a NO-GO** ([`docs/superpowers/spikes/2026-09-04-spike-b-keychain.md`](../spikes/2026-09-04-spike-b-keychain.md)):
    The desktop app had never stored a passphrase, so no real entry existed; against a throwaway entry macOS shows a modal ACL dialog on every access, which a non-interactive session cannot answer. The approach (`security-framework`, generic password, service `Cryptomator`, account = vault ID) is therefore neither confirmed nor refuted — **repeat before M6 with a human at the machine**. **M6 status:** the approach is confirmed for our own entries (round trip in the `keychain_e2e` test); an entry written by Cryptomator.app is still unverified, because the ACL dialog needs a person at the machine.

### `cryptomator-app`

- `settings/model.rs`: `SettingsJson`/`VaultSettingsJson` carrying only the fields we use + `#[serde(flatten)] extra: Map` at both levels; Java defaults (port 42427, useKeychain true, revealAfterMount true, autoLockIdleSeconds 1800, actionAfterUnlock ASK, maxCleartextFilenameLength -1, keychainProvider/mountService per OS); `Option` fields with `skip_serializing_if` (equivalent to `NON_NULL`); legacy keys (`preferredVolumeImpl`, `useCustomMountPath`/`customMountPath`, `winDriveLetter`) are read, migrated and dropped when writing. New entries are written with the full set of Java defaults. Golden tests taken over from `src/test/java/org/cryptomator/common/settings/SettingsJsonTest.java`.
- `settings/store.rs`: paths macOS `~/Library/Application Support/Cryptomator/settings.json`; Linux `~/.config/Cryptomator/settings.json`, then `~/.Cryptomator/settings.json`; override `--settings`/`CRYPTO_SETTINGS_PATH`. Loading is tolerant; saving writes pretty JSON → `settings.json.<pid>.tmp` → rename; `writtenByVersion` is preserved (only on creation `crypto-<semver>`). An unparseable settings.json is an error (a deviation from Java, which silently replaces it).
  **M2 delivers the atomic tmp+rename only.** `flock` on `settings.json.lock` and the warning when the desktop IPC socket is reachable are **deferred to M4**, where the daemon owns the coordination of settings writers anyway (see risk 3). Until then: close the desktop app before `vault add/remove/set` and `config set`.
- `settings/vault_ref.rs`, `settings/ids.rs`: resolution by ID / display name (unique, case-sensitive first) / path (canonicalised); ad-hoc vault by path with `--no-register`; ID = base64url(9 random bytes); `normalize_display_name` (mountName rules).
- `cli_config.rs`: `cli.json` next to settings.json (`mountPointsDir`, `defaultMounter`, `logLevel`, `forceUnmountOnSignalAfterSecs`, `webdavBind`).
- `state_dir.rs`: Linux `$XDG_RUNTIME_DIR/crypto` (fallback `/tmp/crypto-<uid>`, 0700), macOS `~/Library/Application Support/Cryptomator/cli-run`; per vault `<id>.sock/.pid/.json/.log`.
- `keychain/{mod,macos,linux,kde,fake}.rs`: trait `Keychain{store, load, delete, change, is_supported, is_locked, java_class_name, display_name, priority}`; mapping of Java class names ↔ backend (aliases `macos`, `touchid`, `secret-service`, `gnome-keyring`, `kde`/`kwallet`; what gets stored is always the class name); provider choice as in `KeychainModule.provideKeychainAccessProvider`. macOS `security_framework::passwords::*_generic_password("Cryptomator", id)` (override `CRYPTO_KEYCHAIN_SERVICE`; `kSecAttrLabel` = the vault's display name, otherwise the vault ID; migration of old entries under `"Cryptomator\0"` as in `MacKeychain.tryMigratePassword`; `TouchIdKeychainAccess` is mapped onto `MacSystemKeychainAccess` (same items), `change` updates **in place** so that the ACL is preserved); Linux `secret-service` (default collection, fallback `login`; `search_items({"Vault": id})`; `create_item("Cryptomator", {"Vault","Name"}, replace=true)` plus cleanup of superseded items), `GnomeKeyringKeychainAccess` the same backend without `Name`, KDEWallet → "not supported" with a pointer. Wrap async zbus in blocking helpers. Every call runs on a worker thread with a 30 s timeout (support probe 5 s); behind `$CRYPTO_KEYCHAIN_FAKE`, `fake.rs` replaces every real backend with a JSON file and is then the only provider (tests only).
- `password.rs`: order `--password-keychain` (exclusive, **before** everything else; no entry → exit 8) / `--password-stdin` / `--password-file` (≤ 5000 B, strip one trailing newline) / `--password-env` / `CRYPTO_PASSWORD` / keychain implicitly (if `useKeychain`, a provider works here, there is no `--no-keychain` and an entry exists) / TTY prompt (`rpassword`, only on a terminal). `CRYPTO_PASSWORD` deliberately ranks **above** the implicit keychain step: a script variable cannot open a system dialog. New passwords: at least 8 characters, confirmation, NFC normalisation; a *new* password never comes from the keychain.
- `registry.rs`: `VaultRegistry` = settings + state dir → `VaultInfo{id, name, path, state}` including `UNLOCKED@mountpoint` and `STALE_MOUNT`.
- `mounting/mounter.rs`: port of `Mounter.SettledMounter`: service choice (vault.mountService → settings.mountService → first supported one), apply capabilities (FILE_SYSTEM_NAME="cryptoFs", LOOPBACK_PORT: vault.mountService null → settings.port otherwise vault.port, MOUNT_FLAGS: empty → default, VOLUME_ID=id, VOLUME_NAME=mountName, READ_ONLY), mount point policy (validate a user-supplied path; otherwise system-chosen, or create `mountPointsDir/<mountName>` and remove it again on lock).
- `daemon/{protocol,client,server}.rs`: see the daemon design.

### `cryptomator-mount`

- `api.rs`: `MountCapability` (12 variants, Java names), traits `MountService{java_class_name, display_name, is_supported, capabilities, default_mount_flags, default_loopback_port, for_file_system}`, `MountBuilder`, `Mount{mountpoint, unmount, unmount_forced}`, `Mountpoint::{Path, Uri}`.
- `registry.rs`: same order as the Java priorities: macOS `[MacFuse(100), FuseT(90), MacAppleScript(50), Fallback(0), Null]`, Linux `[LinuxFuse(100), LinuxGio(50), Fallback(0), Null]`; lookup by class name; CLI aliases `macfuse`, `fuse-t`, `fuse`, `webdav`, `webdav-applescript`, `webdav-gio`, `null`. Only the mounter of the respective platform is compiled in, but all the class names are (a settings.json from the other platform stays readable). On top of that there is the test mounter `null` (`org.cryptomator.cli.NullMountProvider`), which counts as supported only with `CRYPTO_ENABLE_NULL_MOUNTER=1`, writes a marker file into the mount point instead of mounting, and leaves `conflicting_classes` empty. `conflicting_classes` keeps macFUSE and FUSE-T from running side by side (`MountRequest::running_services`, Java parity).
- `flags.rs`: parser like `AbstractMountBuilder.setMountFlags` (`\s+-` split, set semantics), `-o` → `fuser::MountOption` (typed, otherwise `CUSTOM`), `-r` → RO.
- `transcoder.rs`: macOS FUSE side NFD ↔ vault NFC; Linux identity.
- `fuse/{ops,adapter,session}.rs`: implemented as three layers instead of one file. `ops.rs` (`VaultOps`, `VaultOpsConfig`, `Attr`) holds the vault operations, the inode table (`inodes.rs`), the file/directory handles (`handles.rs`), the errno mapping (`errno.rs`) and the AppleDouble rules; `adapter.rs` is the thin `impl fuser::Filesystem` on top of it (readdir with a limit, getattr/setattr, create/open/read/write/flush/release/fsync, mkdir/rmdir/unlink/rename including NOREPLACE, symlink/readlink, statfs, xattr = ENOTSUP, `setvolname` as a no-op, `READDIRPLUS` = ENOSYS); `session.rs` runs the session on its own thread (`spawn_from_fd(ops, mountpoint, fd, abi, unmounter)`), including unmount, join and unmount error handling. `mount.rs` bundles what both macOS backends share (flags, `macos_ops_config`, `umount_macos` with a 5 s busy retry only on the *graceful* unmount and a reaper thread for an `umount` that does not return).
- `fuse/linux.rs`: class `…LinuxFuseMountProvider`; supported if `fusermount3 -V` (2 s timeout); caps `{MOUNT_FLAGS, MOUNT_TO_EXISTING_DIR}`; default flags `-oauto_unmount -ouid=<uid> -ogid=<gid> -oattr_timeout=5`; mount via `fuser::Session::new` (without the `libfuse` feature, fuser calls `fusermount3`); unmount `fusermount3 -u -- <name>` (cwd parent), forced `fusermount3 -uz` (ours only, cap `UNMOUNT_FORCED`).
- `fuse/macos_dl.rs`: `libloading` of `fuse_mount_compat25`, `fuse_unmount_compat22`, `struct fuse_args`; argv `["cryptomator-cli", "-o", …]`; yields an `OwnedFd` → `fuser::Session::from_fd`.
- `fuse/macfuse.rs`: class `…MacFuseMountProvider`; supported if `/usr/local/lib/libfuse.2.dylib` or `libosxfuse.2.dylib`; caps `{MOUNT_FLAGS, UNMOUNT_FORCED, READ_ONLY, MOUNT_TO_EXISTING_DIR, MOUNT_TO_SYSTEM_CHOSEN_PATH, VOLUME_ID, VOLUME_NAME}`; defaults `-ouid=<uid> -ogid=<gid> -oatomic_o_trunc -oauto_xattr -oauto_cache -onoappledouble -odefault_permissions`; `-ovolname=<name>`, `-r` when read-only; reject `-obackend=fskit`; without a mount point `/Volumes/<volumeId>`; unmount `umount -- <p>` / `umount -f -- <p>`. **Not verified:** macFUSE was not installed on any test machine, this provider has never mounted. `-onoappledouble` is parsed but controls nothing: the `._*`/`.DS_Store` sweep before `rmdir` is driven by the platform, not by the flag (both macOS backends, Java parity `deleteAppleDoubleFiles`), and with macFUSE it is the kernel extension that keeps the sidecars away (`refuse_apple_double = false`).
- `fuse/fuset.rs`: class `…FuseTMountProvider`; supported if `/usr/local/lib/libfuse-t.dylib`; caps `{MOUNT_FLAGS, UNMOUNT_FORCED, READ_ONLY, MOUNT_TO_EXISTING_DIR, VOLUME_NAME}`; defaults **`-ononamedattr -orwsize=262144 -ouid=<uid> -ogid=<gid>`**; always append `-ononamedattr`; same dlopen path. **Implemented as follows:** `-obackend=smb` is gone (spike A: FUSE-T 1.2.7 ships only the NFS helper `go-nfsv4`, `mount -t smbfs` fails with exit 64) — the default backend is NFS. The path does **not** work with an unmodified fuser 0.18 (macFUSE instead of Linux `fuse_attr` layout, spike A); the fork `vendor/fuser` turns the ABI into a **run-time** decision (`Config::abi`, `KernelAbi::{Native, Linux}`) instead of a `cfg`/feature, so that one binary serves macFUSE *and* FUSE-T — demonstrated end to end in spike C (`docs/superpowers/spikes/2026-09-06-spike-c-fuse-t-linux-abi.md`). Two transport fixes from the mount E2E are in the fork as well: requests coalesced by FUSE-T are split up (`Channel::spill`) instead of discarded, and a read of length 0 on the socket is EOF rather than an error. FUSE-T's volume is an NFS mount, hence `refuse_apple_double = true`: macOS' NFS client creates a `._<name>` next to *every* node, which the adapter rejects with `EPERM`, otherwise the vault fills up with encrypted metadata junk.
- `webdav/{fs,server,fallback}.rs`: `impl dav_server::fs::DavFileSystem` over `CryptoFs` (symlinks hidden as in Java); hyper 1 + tokio on `127.0.0.1:<port>` (port 0 → ephemeral), context path `"/" + normalize(volumeId)`; `FallbackMounter` (class `org.cryptomator.frontend.webdav.mount.FallbackMounter`, caps `{LOOPBACK_PORT, VOLUME_ID}`). `MacAppleScriptMounter` and `LinuxGioMounter` are separate services (`webdav/os_mount.rs`) with the Java capabilities and commands (`osascript -e 'mount volume …'` and `gio mount dav://…` respectively, unmount `diskutil umount [force]` and `gio mount -u`); the subprocess helpers live in `process.rs` and are shared with `fuse/mount.rs`. Bind address from `cli.json` (`webdavBind`, loopback only); deviations from webdav-nio-adapter 3.0.2 are listed in the CHANGELOG.

### Daemon design

Implemented in `crates/cryptomator-app/src/daemon/{protocol,client,server,logging}.rs`; the full description of the wire format is in `docs/daemon-protocol.md`. Points 1–6 below have been corrected to the state of the implementation as of M4.

1. `crypto unlock` (the parent process) resolves the vault, obtains the password, runs scrypt + config verification itself (errors surface synchronously) and, when `maxCleartextFilenameLength == -1` and the vault is not read-only, determines the name length via a capability probe and persists it.
2. Creates the state dir; starts `current_exe() __daemon …` with `pre_exec(setsid)`, cwd `/`, stdin `/dev/null`, stdout/stderr → `<id>.log`, environment without `CRYPTO_PASSWORD`. **No `--key-fd`, no `pipe()`:** the 64-byte raw key goes base64-encoded as the *first message* (`op:"unlock"`) over the 0600 socket. The trust boundary is identical (same uid), and the key stays out of `argv`, the environment and any file. Because cwd is `/`, `--settings`, `--state-dir` and `--mount-point` are made absolute before the spawn.
3. Connects to the socket (retry every 100 ms), checks the `hello` (magic + `protocol`), sends `unlock` and waits for the reply `{"mountpoint":…}` or the error `MOUNT_FAILED`; prints the mount point and zeroizes the key. Deadlines are hard-coded: 60 s until the daemon must have seen an `unlock`, 70 s for the whole call — after that SIGTERM before SIGKILL (so that its own unmount still runs) and exit 6 with the last 20 log lines. `--foreground`: the same code path in-process, additionally with `DaemonConfig::notice` — a callback through which the daemon writes the wait before the forced unmount to the caller's stderr (a detached daemon has no terminal and leaves the field `None`).
4. State files: `<id>.pid`, `<id>.sock` (0600), `<id>.json` (`vaultId, path, mounter, mountpoint, pid, startedAt, readOnly`), `<id>.log` (stays behind after the lock). **Write order: pid → socket → run info** (the last one only after a successful mount, because it names the mount point); before each of them a connect probe, so that no running daemon is overwritten. Stale detection in this order: connect to the socket succeeds → `UNLOCKED`; otherwise `kill(pid, 0)` alive → `UNLOCKED` (the window between pid and bind); otherwise the run info's mount point still mounted according to `mount`/`/proc/self/mountinfo` → `STALE_MOUNT` (`lock --force` unmounts via the path); otherwise delete the leftovers.
5. Protocol (newline JSON, the daemon greets first, line limit 1 MiB): `{"hello":"crypto-daemon","protocol":1,"vaultId":…,"pid":…}`; requests `unlock`/`status`/`stats`/`lock`/`events`/`ping`/`shutdown`, tagged via `"op"` with a client `id`; responses `{"id":n,"ok":true,"result":{…}}` or `{"ok":false,"error":{"code":"UNMOUNT_FAILED","message":…}}`; events with `seq`, ring buffer 1000. A follow stream sends `StreamItem`s with the same `id` and closes with exactly one `Response`. **`nextSeq` is the `seq` of the newest event itself** (0 for an empty log) and is read exclusively as `since` (`seq > since`), so it is handed back unchanged.
6. Life cycle: key from the `unlock` message → `Cryptor` → `CryptoFs` (readonly, event sink) → `Mounter` → mount → `<id>.json` → reply. **No tokio:** a `UnixListener` in an accept loop, one thread per connection, one thread each for the stats sampler (1 s, `lastActivity` when the access count grows) and the auto-lock tick, the FUSE session on its own thread; waiting always uses `Condvar::wait_timeout` (cap 100 ms), never a busy loop. tokio lives exclusively in the runtime of the WebDAV server, which the `Mount` owns; the daemon itself stays tokio-free. Shutdown on SIGINT/SIGTERM/**SIGHUP** behaves like `lock`: unmount (graceful, forced after `forceUnmountOnSignalAfterSecs` from `cli.json` — a second signal shortens the wait) → `CryptoFs::close` (flush, zeroize) → delete the state files → exit 0. If the volume survives even the forced unmount, the run info stays behind and the daemon ends with exit 7, so that `status` reports `STALE_MOUNT` and `lock --force` can address the volume.
7. WebDAV port rule (one daemon per vault): `vault.port` if `vault.mountService` is set, otherwise `settings.port`; on `EADDRINUSE` exit 6 with the hint `--port 0`/`vault set --port`. A shared WebDAV host daemon is a later extension. **(Delivered in M5: `MountOverrides.port` / `--port` beats both, `--port 0` takes a free port; `EADDRINUSE` → exit 6 with both ways out in the message.)**

## Open risks

1. ~~**FUSE-T via fuser** (top risk)~~ — **resolved in M4.** Spike A found the struct ABI to be the cause, spike C proved the run-time switch `KernelAbi::Linux` in the fork `vendor/fuser`; the lowlevel FFI backend was not needed. The expected protocol details did in fact show up and are solved: `setvolname` is accepted as a no-op, `READDIRPLUS` answered with ENOSYS, `statfs` is mandatory (FUSE-T sends it as the very first operation), and the stream framing quirks of the FUSE-T socket are handled in the fork.
2. **macOS keychain ACLs**: entries created by Cryptomator.app trigger access prompts in the CLI and vice versa; Touch ID entries may not be readable headless. Signing with a stable identity, plus documentation.
3. **Concurrent settings.json writers**: the desktop app writes the whole file from memory (1 s debounce) → CLI changes made while the app is running can be lost. M2 delivers only the short RMW window with an atomic tmp+rename; flock and the warning when the IPC socket is reachable come with M4 (daemon). Recommendation until then: close the app for `vault add/remove/set` and `config set`.
4. **`.c9u` in-use markers** (only active with a hub owner): ignore them when listing, never create them.
5. **Name normalisation on macOS** (NFD on the FUSE side, NFC in the vault) — implemented in the `NameTranscoder`, demonstrated in the mount E2E. The `._*` files did *not* turn into ordinary encrypted files as planned: under FUSE-T macOS' NFS client creates one next to every node, so there they are rejected with `EPERM`; before `rmdir` both macOS backends sweep away `._*`/`.DS_Store`. Open: whether a Finder copy of a file with xattrs/a resource fork onto a FUSE-T mount fails because of this (manual check).
6. **Java `cleartextSize` error cases** (size 0 for a broken final chunk) have to be reproduced exactly, so that `ls -l` agrees with the desktop app.
7. **RustCrypto version alignment** (digest 0.11) to be checked in M0.
8. ~~**Migration 6→7** is the single biggest item (FilePathMigration, capability probing in `c/`); deliberately late.~~ — **resolved in M7.** `FilePathMigration` (BASE32 → base64url, `0`/`1S` prefixes, `.lng` out of `m/xx/yy/`, `_n` collision resolution) and the capability probing in `c/` are in place; cryptofs 2.10.0 opens the fixtures migrated from 7, 6 and 5. The only thing left open is Java's `REQUIRES_FULL_VAULT_DIR_SCAN` branch, which no local file system triggers.
9. **`fusermount3` is missing in sandboxes** (Flatpak/snap) → the provider is unsupported, WebDAV is the fallback.
